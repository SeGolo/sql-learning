01 Clauses — the skeleton

The building blocks of every query. Written in this order, but run in a different one (see section 08).

ClauseUse it to…ExampleCommon mistake
SELECT Choose which columns to show or compute 
SELECT first_name, salary
 Trailing comma before FROM → "syntax error near FROM"
WHERE Filter rows by a condition (row vs a value) 
WHERE salary > 80000
 Can't use aggregates like COUNT() here — use HAVING
GROUP BY Collapse rows into groups to aggregate 
GROUP BY department
 Every non-aggregated SELECT column must appear here
HAVING Filter groups by an aggregate 
HAVING COUNT(*) >= 2
 Repeat the expression — alias not usable in HAVING
ORDER BY Sort the final rows 
ORDER BY salary DESC
 Text-stored numbers sort as strings ("92000" before "100000")
LIMIT Keep only the first N rows 
ORDER BY salary DESC
LIMIT 10
 LIMIT without ORDER BY → arbitrary rows
DISTINCT Remove duplicate rows from output 
SELECT DISTINCT city
 Applies to the whole row, not one column

02 Filtering operators

Live inside WHERE and HAVING. The boundary and NULL rules here caused most of your early bugs.

OperatorUse it when…ExampleCommon mistake
= <> < > <= >= Compare to a value; <=/>= include the boundary 
WHERE age >= 70
 "more than" = > (excludes); "or more" = >= (includes)
BETWEEN Value in a range, inclusive both ends 
WHERE order_date BETWEEN
'2019-03-01' AND '2019-03-31'
 Inclusive end drops timestamps after midnight — prefer >= start AND < next
IN (…) Value is one of a list 
WHERE department
IN ('HR','Admin')
 Shorthand for many ORs — don't mix up with AND
LIKE Match a text pattern 
WHERE LOWER(name)
LIKE 'draft%'
 %=any chars, _=one char. No wildcard = same as =
IS NULL Test for a missing value 
WHERE phone_number
IS NULL
 = NULL never works — and <> silently drops NULL rows
AND / OR Combine conditions 
WHERE dept IN ('HR','Admin')
AND salary > 80000
 AND binds tighter than OR — parenthesize to be safe

03 Aggregate functions

Squash many rows into one number — per group with GROUP BY, or over the whole table.

FunctionGives you…ExampleCommon mistake
COUNT(*) Number of rows 
SELECT COUNT(*) FROM orders
 Counts NULL rows too — after a LEFT JOIN that over-counts
COUNT(col) Non-NULL values in a column 
COUNT(phone_number)
 Ignores NULLs — different number from COUNT(*)
COUNT(DISTINCT col) How many different values 
COUNT(DISTINCT unit_id)
 Forgetting DISTINCT counts repeats
SUM(col) Total 
SUM(total_order_cost)
 On text-typed columns → error; CAST first
AVG(col) Average 
AVG(salary)
 Skips NULLs — not the same as treating them as 0
MIN / MAX(col) Smallest / largest 
MAX(salary)
 On text columns, "max" is alphabetical, not numeric

04 Joins — combine tables side by side

Joins add columns. The ON is just a condition — usually a foreign key, but it can compare any columns.

JoinUse it when you want…ExampleCommon mistake
INNER JOIN Only rows matching in both tables 
FROM orders o
INNER JOIN customers c
  ON o.cust_id = c.id
 Joining id = id — use the foreign key (cust_id)
LEFT JOIN All left rows + matches (NULL where none) 
FROM customers c
LEFT JOIN orders o
  ON c.id = o.cust_id
 Filtering the right table in WHERE turns it back into an INNER JOIN
RIGHT JOIN All right rows + matches 
FROM customers c
RIGHT JOIN orders o
  ON c.id = o.cust_id
 Rarely needed — usually clearer to flip to LEFT
FULL OUTER JOIN All rows from both sides 
FULL OUTER JOIN orders o
  ON c.id = o.cust_id
 Not in MySQL — emulate with LEFT ... UNION ... RIGHT
CROSS JOIN Every combination of every row 
FROM nums a
CROSS JOIN nums b
 No ON — produces N×N rows (all pairs)
Self-join Compare a row to other rows in the same table 
SELECT DISTINCT
  e1.first_name AS higher_earner,
  e1.department,
  e1.salary
FROM employees e1
JOIN employees e2
  ON e1.dept = e2.dept
 AND e1.salary > e2.salary
 Needs two aliases; produces duplicates → add DISTINCT
Self-join 2 Find all pairs of employees in the same department. 
SELECT
  a.first_name AS employee1,
  b.first_name AS employee2,
  a.department
FROM employee a
JOIN employee b
  ON a.department = b.department -- same department
  AND a.id <> b.id -- avoid self-pair
  -- The a.id <> b.id condition is important.
  -- Without it, every employee gets paired with themselves.
Needs a name and a query; can be referenced multiple times in the main query
Self-join 3 List every worker who shares a salary with someone else. The 2nd copy is only a test — it is not in the output. 
SELECT DISTINCT
  w1.worker_id,
  w1.first_name AS name,
  w2.salary   AS payment
FROM worker w1
JOIN worker w2
  ON w1.worker_id <> w2.worker_id  -- "any OTHER worker"
WHERE w1.salary = w2.salary
 Use <>, not < — so both workers of a matching pair get a row. DISTINCT collapses repeats.
Self-join 4 All number pairs whose product exceeds 11. Both numbers are the output. 
SELECT DISTINCT
  n1.number AS num1,
  n2.number AS num2
FROM transportation_numbers n1
JOIN transportation_numbers n2
  ON n1.index < n2.index        -- keep ONE ordering
WHERE n1.number * n2.number > 11
 <> here would output (2,7) and (7,2) — the same pair twice.
Self-join keys: <> vs < / > — it turns on whether the second copy of the table is part of the answer or just an existence test.
  • Second copy is shown in the output (a pair, e.g. num1, num2 — Self-join 4) → use < or >. (2,7) and (7,2) are the same pair, so < keeps one ordering and also removes self-pairs.
  • Second copy is only a test ("does another row exist where…?" — only the first copy is output — Self-join 3) → use <>. You need "any other row", and every row must be able to play the first-copy part, so < would silently drop some.
  • Set-theory view: < yields each unordered pair {a, b} once; <> yields every ordered pair (a, b) with a ≠ b — both directions.
Ordering JOIN chains
  • Start FROM the table that holds what you're measuring. Revenue comes from quantity × price, so start with order_items. That table is your “fact” table.
  • Each ON may only use tables that are already introduced. SQL reads top-down, so ON can reference the new table plus anything above it, never anything below it. 
    FROM order_items oi
JOIN orders o     ON o.order_id = oi.order_id        -- oi is above ✔
JOIN products pr  ON pr.product_id = oi.product_id   -- oi is above ✔
JOIN categories c ON c.category_id = pr.category_id  -- pr is above ✔
    Classic bug: o.order_id = pr.order_id, which uses pr before it exists.
  • Follow the foreign keys like a path. Ask “which column links the new table to something I already have?” If nothing links yet, join the bridge table first. Categories can only be reached through products, so products must come before categories.
  • Write ON as new.key = existing.key. Put the new table on the left of = every time. Then you can see at a glance that the right side points to a table above. (The order inside ON doesn't change the result; it's only a readability habit.)
  • Draw the path before writing. For example: categories ← products ← order_items → orders. Start in the middle (the fact table) and walk outward along the arrows, one JOIN per arrow.
  • Use short, distinct aliases and stick to them. For example oi, o, p, cat. After writing the query, check that every alias in SELECT, WHERE and GROUP BY appears in FROM/JOIN.
  • Quick check: read each ON line and ask whether both aliases are defined at or above that line. If one isn't, the line is in the wrong place or uses the wrong alias.

05 Stacking rows

Where joins add columns, these add rows — two result sets on top of each other. Both halves need the same column count and order.

KeywordUse it to…ExampleCommon mistake
UNION Stack two results, remove duplicates 
SELECT 'customers', COUNT(*) FROM customers
UNION
SELECT 'orders', COUNT(*) FROM orders
 Column count/order must match both halves
UNION ALL Stack two results, keep duplicates (faster) 
SELECT dept FROM a
UNION ALL
SELECT dept FROM b
 Duplicates the rows — use plain UNION if you need unique

06 Row-level functions

Transform a value per row. These clean, convert, and label your data — the daily work of data quality.

FunctionUse it to…ExampleCommon mistake
CASE WHEN If/else per row: label, bucket, or flag 
CASE WHEN salary < 75000 THEN 'low'
     WHEN salary < 100000 THEN 'mid'
     ELSE 'high' END
 Order matters — first match wins; overlapping ranges mis-bucket
COALESCE(a,b,…) First non-NULL value (default for NULLs) 
COALESCE(phone, 'none')
 Arguments must be compatible types
NULLIF(a,b) Return NULL if a = b 
x / NULLIF(COUNT(*), 0)
 Wrap the denominator to dodge divide-by-zero, not the whole thing
CAST(x AS type) Convert type (text → number) 
CAST(age AS INTEGER) > 40
 Skipping it → string comparison ("9" > "40" is true)
LOWER / UPPER Normalize case before comparing 
WHERE LOWER(dept) = 'hr'
 LOWER(x) = 'HR' never matches — compare to lowercase
REPLACE(x,…) Strip / swap characters 
REPLACE(LOWER(device),' ','')
 Only removes exact matches — case still needs LOWER
GREATEST / LEAST Larger / smaller of several values 
GREATEST(a.number, b.number)
 A NULL argument can make the whole result NULL
ROUND(x,n) Round to n decimals 
ROUND(count/total * 100, 2)
 Watch the parens — ROUND(value, 2), both inside

07 Counting a condition

SQL has no "count only the matching rows" function — you fake it by turning the condition into 1s and 0s, then summing. Three spellings, same answer.

PatternUse it to…ExampleCommon mistake
SUM(CASE…) Count rows matching any condition 
SUM(CASE WHEN phone IS NULL
    THEN 1 ELSE 0 END)
 The 0s don't affect the total — only the 1s count
COUNT(CASE…) Same, via NULL-skipping 
COUNT(CASE WHEN phone IS NULL
      THEN 1 END)
 Omit ELSE so non-matches become NULL & are skipped
COUNT(*) - COUNT(col) Count the NULLs specifically 
COUNT(*) - COUNT(phone)
 —
COUNT(condition) Does NOT work — avoid 
COUNT(phone IS NULL)  -- wrong
 A boolean is never NULL → counts every row

08 The key mental model — execution order

You write the clauses in one order, but SQL runs them in another. This single fact explains most of the "why can't I…" bugs.

FROM→ WHERE→ GROUP BY→ HAVING→ SELECT→ ORDER BY
  • WHERE can't use COUNT/SUM — aggregates don't exist until after GROUP BY, so filter groups with HAVING.
  • Aliases work in ORDER BY but not HAVING/WHERE — the alias is born in SELECT, which runs late.
  • SELECT — where you build aliases and computed columns — happens almost last.
