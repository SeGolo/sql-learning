00 The key mental model — execution order

You write the clauses in one order, but SQL runs them in another. This single fact explains most of the "why can't I…" bugs.

StepClause
1FROM
2WHERE
3GROUP BY
4HAVING
5SELECT
6DISTINCT
7ORDER BY
8LIMIT
  • WHERE can't use COUNT/SUM — aggregates don't exist until after GROUP BY, so filter groups with HAVING.
  • Aliases work in ORDER BY but not in WHERE or HAVING — the alias is born in SELECT, which runs late. Exception: PostgreSQL and MySQL also let you write the alias in GROUP BY (a shortcut they add); Oracle does not.
  • SELECT — where you build aliases and computed columns — happens almost last.

How a query really runs

Think of a query as a production line. Each step receives a table, changes it, and passes a new table to the next step. A step can only see what the steps before it produced. The database may work differently inside to gain speed, but the result is always the same as if it followed this order.

Follow the example below on the staff table. It has no DISTINCT, so it skips step 6:

  1. FROM takes all 5 rows.
  2. WHERE salary >= 50000 leaves 4 rows. Jan goes, because a NULL salary does not pass the test.
  3. GROUP BY dept makes 3 groups: HR, IT, Sales.
  4. HAVING AVG(salary) > 60000 removes HR (average 55000).
  5. SELECT builds the columns. Only now does the name avg_pay exist.
  6. ORDER BY avg_pay DESC can use that name: IT, then Sales.
  7. LIMIT 1 keeps IT.

How to use this

Plan a query in running order, not written order. First ask which tables you need, then which rows, which groups, and only at the end which columns to show.

Table: staff

idnamedeptsalaryphone
1AnnaHR50000777 111
2PetrHR60000NULL
3EvaIT80000777 333
4JanITNULL777 444
5LucieSales70000NULL

Example:

A full query

Written top to bottom, run in the order of the numbers. No DISTINCT here, so step 6 is skipped

When to use:

  • Error column "x" does not exist on an alias: the clause runs before SELECT created it
  • Choosing the filter: on rows → WHERE; on a COUNT or SUM → HAVING
  • Planning a long query: tables first, then filters, groups, columns, and the sort last
SELECT dept, AVG(salary) AS avg_pay   -- 5
FROM staff                            -- 1
WHERE salary >= 50000                 -- 2
GROUP BY dept                         -- 3
HAVING AVG(salary) > 60000            -- 4
ORDER BY avg_pay DESC                 -- 7
LIMIT 1                               -- 8

Output:

deptavg_pay
IT80000

⚠ Mistake: HAVING avg_pay > 60000 → error: avg_pay is born in step 5, HAVING runs in step 4

01 Data types — what a column holds

Every column has a type, and most surprising results come from it: integer division, text that looks like a number, dates vs timestamps. Names are PostgreSQL; MySQL and Oracle differ slightly.

The idea

A type decides three things about a column: which values it accepts, which operations work on it, and how its values compare and sort. The same characters can behave differently: as numbers, 100 is larger than 92; as text, '100' sorts before '92', because text is compared one character at a time and 1 comes before 9.

How it works

  • The inputs decide the result type. Integer / integer gives an integer, so 7 / 2 = 3. Integer / decimal gives a decimal, so 7 / 2.0 = 3.5.
  • Exact or approximate. NUMERIC stores the exact digits. DOUBLE PRECISION stores a close binary value, because a number like 0.1 has no exact binary form. That is fast and fine for measurements, but not for money.
  • Conversions. A quoted value such as '2024-03-01' becomes a date when you compare it with a date column. A column does not convert by itself: if age is text, age > 40 is an error in PostgreSQL. Use CAST.
  • NULL fits every type. It means "unknown value", not zero and not empty text.

How to choose

Counted → INTEGER. Money → NUMERIC. Measured → DOUBLE PRECISION. A day → DATE. A moment → TIMESTAMP. Digits you never calculate with, such as phone numbers → TEXT. When you meet a new table, check the column types before you write anything.

Approximate decimals: measurements, ratios

  • Scientific or statistical results where a tiny error is fine
  • Never for money

When to use:

  • VARCHAR(n) when a length limit is a real rule, e.g. a 20-character username

Fixed-length text, padded with spaces

When to use:

  • Codes that always have the same length: country CZ, currency CZK
  • Reading older database designs that use it
  • Otherwise prefer VARCHAR or TEXT

true / false / NULL

When to use:

  • Yes/no flags: is_active, in_stock, is_vip

02 Clauses — the skeleton

The building blocks of every query. Written in this order, but run in a different one (see section 00).

The idea

Each clause answers one question:

  • FROM: where does the data come from?
  • WHERE: which rows count?
  • GROUP BY: which rows belong together?
  • HAVING: which groups count?
  • SELECT: what do I show?
  • ORDER BY and LIMIT: in which order, and how many?

The result of a query is always a table, so it can be read by another query (section 06).

The most important question: what is one row?

Before writing, finish this sentence: "one row of my result is one …". One employee means no GROUP BY. One department means GROUP BY dept. Most wrong results come from answering at the wrong level.

From a question to a query

"Departments with at least 2 people whose salary is known." One row = one department. The clauses follow from the words:

SELECT dept, COUNT(*) AS people   -- what to show
FROM staff
WHERE salary IS NOT NULL          -- "whose salary is known": a test on rows
GROUP BY dept                     -- one row per department
HAVING COUNT(*) >= 2              -- "at least 2": a test on groups

The result is HR, with 2 people. IT has only Eva left, because Jan's salary is NULL.

Rows have no natural order

A table is a set of rows, not a list. Unless you write ORDER BY, the database can return them in any order, even if it looks stable today.

03 Filtering operators

Live inside WHERE and HAVING. The boundary and NULL rules here caused most of your early bugs.

The idea

WHERE tests each row and keeps it only if the answer is TRUE. There are three possible answers, not two: TRUE, FALSE and UNKNOWN. Any comparison with NULL gives UNKNOWN, because you cannot say whether an unknown value equals something. A row with UNKNOWN is dropped, the same as FALSE.

How AND, OR and NOT handle UNKNOWN

ExpressionResultWhy
TRUE AND UNKNOWNUNKNOWNdepends on the unknown side
FALSE AND UNKNOWNFALSEone FALSE is enough
TRUE OR UNKNOWNTRUEone TRUE is enough
FALSE OR UNKNOWNUNKNOWNdepends on the unknown side
NOT UNKNOWNUNKNOWNstill unknown

So coupon <> 'SPRING' does not return rows without a coupon: for them the test is UNKNOWN. To keep them, ask for it: coupon <> 'SPRING' OR coupon IS NULL.

Order of evaluation

SQL applies NOT first, then AND, then OR, the way multiplication comes before addition. Use parentheses whenever you mix AND and OR.

Turning conditions around

To negate a combined condition, flip each part and swap AND with OR: NOT (a AND b) is NOT a OR NOT b. "Not (paid and over 100)" means "not paid, or not over 100".

How to read the task

  • "More than 100" excludes 100. "At least 100" includes it.
  • "In March" on a timestamp: from the start of March up to, but not including, the start of April.
  • Whenever you write <> or NOT, ask: can this column be NULL, and do I want those rows?

04 Aggregate functions

Squash many rows into one number — per group with GROUP BY, or over the whole table.

The idea

An aggregate takes many values and returns one. The difference between the two forms is only how many groups there are:

  • No GROUP BY: the whole table is one group, so you get one row.
  • With GROUP BY dept: rows are sorted into piles, one per department, and each pile gives one row.

Why other columns are not allowed

After grouping, HR is one row but contains two people. If you ask for name, the database cannot know whether to show Anna or Petr, so it raises an error. In SELECT you can only use grouped columns and aggregates.

Three rules worth remembering

  • NULLs are skipped by every aggregate except COUNT(*), which counts rows. That changes averages: the IT average below is 80000 because only Eva has a salary.
  • No rows in, what comes out? COUNT gives 0. SUM, AVG, MIN and MAX give NULL, not 0.
  • No aggregate inside an aggregate. AVG(COUNT(*)) is an error. Do it in two steps: count per group in a subquery, then average (section 06).

How to think about it

Filter before grouping if the condition is about a row (WHERE). Filter after grouping if it is about the whole group (HAVING). Words such as "per", "each" and "by" usually point to the GROUP BY column.

05 Joins — combine tables side by side

Joins add columns. The ON is just a condition — usually a foreign key, but it can compare any columns.

The idea

Good databases split data into separate tables so that each fact is stored once. A customer's name sits in customers; each order only stores cust_id. That column is a foreign key: a value pointing to a row in another table. A join puts the pieces back together.

How it works

Imagine two steps. First, pair every row of one table with every row of the other. Second, keep the pairs where ON is TRUE. Outer joins then add back the rows that found no partner, with NULLs in the missing columns. With the sample tables below:

  • All pairs: 3 customers × 4 orders = 12.
  • INNER JOIN: ON is TRUE for 3 pairs → 3 rows.
  • LEFT JOIN: adds Eva, who has no orders → 4 rows.
  • RIGHT JOIN: adds order 13, which has no customer → 4 rows.
  • FULL OUTER JOIN: adds both → 5 rows.

How many rows will I get?

Ask this before every join, because it is where totals go wrong:

  • One-to-one: the row count stays the same.
  • One-to-many: the "one" side repeats once per match. Anna has 2 orders, so she appears twice. A SUM on a column from her side would count it twice.
  • Many-to-many: matches multiply. See Fan-out below.

ON or WHERE?

ON decides what counts as a match. WHERE runs afterwards and removes rows from the joined result. For an inner join the two give the same result. For an outer join they differ: a WHERE test on the right table removes the rows filled with NULLs, which were the reason for using the outer join.

How to choose

Do I need rows that have no match? No → INNER. Yes, from one side → LEFT. From both sides → FULL. A NULL key never matches anything, even another NULL.

Self-join keys: <> vs < / > — it turns on whether the second copy of the table is part of the answer or just an existence test.
  • Second copy is shown in the output (a pair, e.g. num1, num2 — Self-join 4) → use < or >. (2,7) and (7,2) are the same pair, so < keeps one ordering and also removes self-pairs.
  • Second copy is only a test ("does another row exist where…?" — only the first copy is output — Self-join 3) → use <>. You need "any other row", and every row must be able to play the first-copy part, so < would silently drop some.
  • Set-theory view: < gives each pair once; <> gives it twice, A–B and B–A. (Formally: < yields each unordered pair {a, b} once; <> yields every ordered pair (a, b) with a <> b.)
Ordering JOIN chains
  • Start FROM the table that holds what you're measuring. Revenue comes from quantity * price, so start with order_items. That table is your “fact” table (the main table you measure).
  • Each ON may only use tables that are already introduced. SQL reads top-down, so ON can reference the new table plus anything above it, never anything below it. 
    FROM order_items oi
JOIN orders o     ON o.order_id = oi.order_id        -- oi is above ✔
JOIN products pr  ON pr.product_id = oi.product_id   -- oi is above ✔
JOIN categories c ON c.category_id = pr.category_id  -- pr is above ✔
    Classic bug: o.order_id = pr.order_id, which uses pr before it exists.
  • Follow the foreign keys like a path. Ask “which column links the new table to something I already have?” If nothing links yet, join the bridge table (the in-between table that links two others) first. Categories can only be reached through products, so products must come before categories.
  • Write ON as new.key = existing.key. Put the new table on the left of = every time. Then you can see at a glance that the right side points to a table above. (The order inside ON doesn't change the result; it's only a readability habit.)
  • Draw the path before writing. For example: categories ← products ← order_items → orders. Start in the middle (the fact table) and walk outward along the arrows, one JOIN per arrow.
  • Use short, distinct aliases and stick to them. For example oi, o, p, cat. After writing the query, check that every alias in SELECT, WHERE and GROUP BY appears in FROM/JOIN.
  • Quick check: read each ON line and ask whether both aliases are defined at or above that line. If one isn't, the line is in the wrong place or uses the wrong alias.

06 Subqueries & NULL traps

A query inside another query: as a list (IN), a test (EXISTS), one value, or a table. NULL is "unknown", so comparisons with it are never true — the source of the nastiest traps.

The idea

A subquery splits a hard question into two easier ones: the inner query answers the small question, the outer query uses the answer. "Orders above average" becomes: what is the average? Which orders are above it?

What it returns decides where it goes

ReturnsUse with
one value=, >, <
one columnIN, NOT IN
a whole tableFROM (needs an alias)
rows or no rowsEXISTS, NOT EXISTS

Correlated subqueries

A normal subquery gives one answer for the whole outer query. A correlated one mentions a column of the outer query, so think of it as running again for each outer row: for each client, "is there a purchase with this client's id?".

Why one NULL breaks NOT IN

x NOT IN (1, NULL) means x <> 1 AND x <> NULL. For Petr, id 2: 2 <> 1 is TRUE, 2 <> NULL is UNKNOWN, and TRUE AND UNKNOWN is UNKNOWN (section 03). The row is dropped, and the same happens to every row. NOT EXISTS does not have this problem, because it only asks whether a matching row exists.

Subquery or join?

  • You need columns from the other table → JOIN.
  • You only need to test something → IN or EXISTS. They never repeat rows: a JOIN to purchases shows Anna twice, IN shows her once.
  • You need to aggregate twice, or to aggregate before joining → subquery in FROM.

07 Stacking rows

Where joins add columns, these add rows — two result sets on top of each other. Both halves need the same column count and order.

The idea

A join adds columns: it places tables side by side. These keywords add or compare rows: they place results on top of each other. Use them when both results are the same kind of thing, such as customers of 2023 and customers of 2024. If the second table describes the first with extra details, you need a join.

How it works

  • Columns match by position, not by name. Both halves need the same number of columns, with compatible types. The output takes its column names from the first SELECT.
  • Whole rows are compared. Two rows are "the same" only if every column matches. Here, unlike with =, NULL counts as equal to NULL.
  • Duplicates are removed unless you write ALL.

Think of two circles

With the samples below, 2023 = {1, 2, 2, 3} and 2024 = {2, 3, 4}:

  • UNION, in either: 1, 2, 3, 4.
  • INTERSECT, in both: 2, 3.
  • EXCEPT, in the first only: 1.
  • UNION ALL, simply everything: 7 rows.

Order of evaluation

INTERSECT runs before UNION and EXCEPT. With three or more results, use parentheses.

08 Row-level functions

Transform a value per row. These clean, convert, and label your data — the daily work of data quality.

The idea

A row function takes values from one row and returns one value for that row. The number of rows does not change. That is the opposite of an aggregate, which turns many rows into one. You can use a row function anywhere a value fits: in SELECT, WHERE, GROUP BY, ORDER BY, and inside an aggregate.

Nested functions run from the inside out

REPLACE(LOWER(device), ' ', '')
'Smart Phone'  → LOWER   → 'smart phone'
'smart phone'  → REPLACE → 'smartphone'

Read them from the middle, and write them one step at a time.

NULL goes in, NULL comes out

Most functions return NULL when an input is NULL: LOWER(NULL) and LENGTH(NULL) are NULL. Some are made to handle it: COALESCE replaces it, CONCAT skips it, and CASE can test for it.

How CASE decides

It tests the conditions from top to bottom and stops at the first TRUE. So each later condition already knows the earlier ones failed: in the salary example below, salary < 100000 only sees salaries of 75000 or more. With no match and no ELSE, the result is NULL. A NULL value fails every comparison, so it falls through to ELSE: test IS NULL first if that matters.

Row functions and aggregates work together

In SUM(CASE WHEN … THEN 1 ELSE 0 END), the CASE runs once per row and SUM then adds up the results. Section 10 builds on this.

09 Dates & times

Group by period, pick parts of a date, shift and subtract dates. Most date bugs are about a time hiding inside a TIMESTAMP, or about which day is "today".

The idea

There are three kinds of time value. A DATE is a day on the calendar, a TIMESTAMP is an exact moment, and an INTERVAL is a length of time. The type of the result depends on the inputs:

CalculationResult
date + numberdate
date - datenumber of days
timestamp - timestampinterval
timestamp + intervaltimestamp
date + intervaltimestamp

Timeline or cycle?

This choice decides which function you group by:

  • Timeline, such as a sales trend: use DATE_TRUNC. It keeps the year, so January 2023 and January 2024 stay separate.
  • Cycle, such as the busiest weekday or month in general: use EXTRACT. It drops the rest, so all Mondays become one group.

Filter periods with a closed start and an open end

Write >= start AND < next_start. This works for DATE and TIMESTAMP, needs no thinking about month lengths, and never counts a row twice when periods sit next to each other.

Empty periods do not appear

GROUP BY can only make groups from rows that exist. In the sample below there is nothing in February, so the DATE_TRUNC output jumps from January to March instead of showing 0. For a full list of months, make the months first with generate_series and LEFT JOIN your data to them.

10 Counting a condition

Standard SQL has no "count only the matching rows" function — you fake it by turning the condition into 1s and 0s, then summing. Several spellings, same answer (PostgreSQL's FILTER is the shortcut).

The idea

WHERE removes rows from the whole query, so it can answer only one question at a time. To count several things side by side, keep all the rows and make each aggregate look only at the rows it wants. This is called conditional aggregation.

How it works

CASE runs once per row and turns the condition into a value. The aggregate then treats those values as usual:

  • SUM: THEN 1 ELSE 0 → adding up 1s and 0s counts the matches.
  • COUNT: THEN 1 with no ELSE → non-matches become NULL, and COUNT skips NULLs.
  • AVG: THEN 1 ELSE 0 → the average of 1s and 0s is the share. For phones missing in staff: 0, 1, 0, 0, 1 averages 0.4, which is 40%.

Why WHERE is not the same

Count missing phones per department. IT has none:

-- WHERE: IT disappears, you get only HR and Sales
SELECT dept, COUNT(*) AS no_phone
FROM staff
WHERE phone IS NULL
GROUP BY dept

-- CASE: all 3 departments stay, IT shows 0
SELECT dept,
       SUM(CASE WHEN phone IS NULL THEN 1 ELSE 0 END) AS no_phone
FROM staff
GROUP BY dept

How to choose

One condition and no need to see zero groups → WHERE. Several conditions in one row, a share of the total, or groups that must show 0 → conditional aggregation.

11 Coming next — advanced

Not learned yet. Window functions are the dividing line between "basic" and "pokročilá znalost SQL" — learn them next.

The idea

GROUP BY squashes rows: you get the department average, but you lose the people. A window function calculates over a group of rows and keeps every row: each person stays, with the department average next to them.

The parts of OVER (…)

  • PARTITION BY dept: split the rows into groups. Without it, all rows are one group.
  • ORDER BY salary DESC: sort inside each group. Ranking and LAG need this.

Adding ORDER BY to SUM changes what it does: it now adds up the rows so far, which gives a running total.

Three ways to rank

For the salaries 80, 60, 60, 40:

FunctionResultOn a tie
ROW_NUMBER1, 2, 3, 4picks an order; tied rows get different numbers
RANK1, 2, 2, 4same number, then a gap
DENSE_RANK1, 2, 2, 3same number, no gap

Where they run

Window functions run after WHERE, GROUP BY and HAVING (section 00), so you cannot filter on them in those clauses. Calculate them in a CTE or subquery, then filter in the outer query.

CTE: naming a step

WITH name AS (…) gives a subquery a name and lets you read the query from top to bottom, like a recipe. The name exists only for that one statement. Each step can use the steps before it.

WITH name AS (…)

Name a sub-result; build a query in readable steps (CTE)

When to use:

  • A long query split into named steps
  • Filter on a window function: rank in the CTE, WHERE after it
  • Aggregate first and join after, to avoid fan-out
WITH ranked AS (
  SELECT name, dept, salary,
         RANK() OVER (PARTITION BY dept ORDER BY salary DESC) AS rnk
  FROM team
)
SELECT name, dept, salary FROM ranked
WHERE rnk = 1
ORDER BY dept
